## 1 am_liam
You need an app with AI in it, on Postgres. With sign-in, access to a model, secrets, and a deploy. That is weeks of plumbing before the first useful screen.

Here are five apps that already have all of it. They are not only demos of AgentPG. They are templates: take one, adapt it, and run it for a real use case.

Full sign-in, a model gateway, secrets, service-to-service integration, and a full deploy process are already in place. The five apps are Apache 2.0.

And the whole fleet, eight sandboxes with their databases, deploys from one manifest in about fourteen minutes.

## 2 af_heart
Here is the map, with three labels.

The platform is EDB Postgres on AgentPG: a database and a sandbox for every app, with the EDB extensions.

Reference scaffolding is identity, the LLM gateway, and the kit vault. All swappable: any OIDC provider that sends the roles the apps expect, any OpenAI-compatible gateway, your own vault through the kit.

The sample apps sit on top. The simulator sends readings to CityPulse. CityPulse reports trouble to PagerLens. ShopFront sends payments to PayBroker, and a signed webhook comes back. Every app asks the gateway for its model.

And everything signs in through identity, with short-lived service tokens.

## 3 am_eric
TrustDesk is a compliance workspace. An approver has a stack of employee requests, and a long policy handbook.

A model checks each request against the policy. The answer lists numbered reasons, and each one quotes the policy.

The app checks every quote against the document, word for word. A person still decides.

Instead of a separate search stack, search is pgvector, full-text, and pg_trgm in one Postgres, so typos still find the right policy. Personal data sits behind masked views, not behind code in every service.

It signs in through identity, and asks the gateway for its model.

## 4 af_heart
PagerLens is an incident investigator. It is three in the morning, and an alert fires.

It gathers the evidence, ranks likely causes, and shows the data that supports or refutes each one. It can read, but it cannot restart or roll back anything.

Ask PagerLens answers in plain English, and each citation is marked verified against the database. Here, a labelled stand-in model answers.

Live incident pages come from Postgres itself, through tcn notifications, so there is no message broker. Tuning is propose and approve: nothing is applied by default.

It receives alerts from CityPulse, and signs in through identity.

## 5 am_liam
CityPulse watches a smart city. Thousands of simulated sensors report through a real collection path, and a status engine turns the readings into a city verdict.

The simulator feeds it, with a short-lived token from identity. Press burst, and the city degrades.

CityPulse reports its own health to PagerLens, and PagerLens opens an incident.

The city is real: Brussels, with real commune outlines from OpenStreetMap, and simulated sensors placed inside them.

One SQL statement answers a district question across relational, time series, JSON, geographic, and vector data. PostGIS answers distance questions in metres: the nearest healthy sensors are 101, 176, and 249 metres away. It replaces a separate GIS server. Readings are partitions, and sensor metadata is JSONB.

## 6 af_heart
PayBroker is a payment broker. One API in front of several simulated processors, with smart routing and a three-tier fraud engine. It takes test cards only.

Every decision goes into a hash-chained audit ledger, inside Postgres. Change one old row, and verify names the first broken entry.

Row-level security keeps each merchant to its own rows, and masked views hide what the read-only user should not see. Both live in the database, not in every service.

Payments are idempotent: a retry never charges twice. ShopFront calls it, and PayBroker sends signed webhooks back.

## 7 am_eric
ShopFront is a small web shop. It shows an ordinary app, on a database that works.

Search forgives typos: kettel finds kettle. A vague query like morning caffeine matches by words and by meaning, in one SQL statement, with no separate vector store.

At checkout, the card goes from the browser straight to PayBroker, so the shop never sees the number. A signed webhook comes back, and the order page updates live through tcn, with no message broker.

It is the easiest one to copy: a catalog, a cart, orders, and payments through another service.

## 8 af_heart
How do they integrate? Five things, all swappable.

Sign-in is OIDC, with roles per app.

Model access is one gateway door, with a key and limits for each app.

Service calls use short-lived tokens that carry scopes, so CityPulse may call PagerLens, and nothing else.

Webhooks are signed, between ShopFront and PayBroker.

Secrets live in the kit vault, never in code or in files.

And every app gets the same extras from the shared kit: an Insights tab, health checks, and masking.

## 9 am_liam
Now the platform. Every app has a Database page, fed by edb_stat_monitor for top queries, edb_pg_tuner for settings, and query_advisor for index suggestions. No external monitoring or tuning tool.

These are suggestions only. A person decides what to change.

Masking is Postgres done properly. Base tables are revoked, masked views are the way in, and the kit keeps it in force. The read-only user an AI connects with cannot read what is masked.

So it is one Postgres, instead of a search engine, a vector database, a map server, and a message queue.

Two MCP routes exist: each app's own MCP server, and AgentPG's database MCP.

## 10 af_heart
Next on the roadmap: EDB AIDB. We are integrating it into the apps.

The plan is pipelines that chunk and embed documents inside the database, and keep them in step when the source table changes. So the apps stop computing embeddings in application code.

TrustDesk policies, PagerLens runbooks and incident memory, and CityPulse questions in plain language are the first candidates.

And agents that run inside Postgres, with tools that act as a database role. The grant, not a prompt, sets what an AI may touch.

## 11 am_eric
To run them: each repository has a README quick start and a Dockerfile.

ecoctl is an internal tool. One manifest, one command, and the whole fleet is deployed. It was built to show how you can wrap your own solution around the agentpg client.

There are also Ansible recipes that deploy the whole fleet on AgentPG. They are tested, and they work: all eight apps, deployed from empty, in about fourteen minutes.

They are a sample to reuse, to fit your company's own deployment. The same manifest as ecoctl, ansible-core only, and three playbooks: site, verify, and destroy.
