## 1 am_liam
The five apps in this ecosystem are templates, released under the Apache License, version two. Take one, adapt it, run it.

But you do not have to take an app. Their building blocks can be used alone. If all you need is sign-in, or a vault for secrets, or one door to your language models, you can take just that.

This is a tour of those blocks. For each one you will hear what problem it solves, how to take only that block, what the apps use it for, and what you would otherwise have to build. Where we can, we run the real code, here, on this machine. Every screen is labeled: local run, captured from the live fleet with its date, or slide.

## 2 af_heart
We sorted the blocks into eight groups: identity and access, data and Postgres, AI access, security and governance, observability and tuning, web and UI, deployment and operations, and patterns inside the apps.

Each block has one of three statuses. A library is a package you import. A service runs alone, with only a Postgres behind it. A pattern to copy is good code that lives inside an app: sometimes one file that lifts out as is, sometimes a design to re-implement. We say which, and we never call a pattern a component.

Most libraries live in one package, the kit, under the Apache License, version two. It installs with pip, from a release tag, or from a clone, as here. This is version zero point three point one.

## 3 am_eric
Do we have authentication as a component? Yes. In the kit it is a module called auth, and the identity service is the provider behind it.

Here is a whole protected endpoint, in fifteen lines. The app says what its roles and scopes mean, as permissions. The route asks for one permission. The same line accepts a browser session, an API token, or a token from an identity provider.

Without a token: four oh one. A token whose scope has no such permission: four oh three. A token with the read scope: the data.

Otherwise you would build sessions, hashed tokens, scopes, a permission check, and a limit on failed logins. Every app here uses this one module for all of it.

## 4 af_heart
Now the same endpoint, with a real identity provider. This is the identity service, running locally: a standalone OpenID Connect provider, with its own console.

We registered a calling service and asked for a token. The provider signed it. The app needs two environment variables, the issuer address and its client identifier, and its code does not change.

The service token opens the endpoint. A token with one character added is refused. And the local API token still works beside it.

Identity is swappable: any OpenID Connect provider that sends the roles the app expects will do. Services get short-lived tokens through the kit's token source.

## 5 am_liam
The vault keeps the secrets an app must store: a model provider's key, a webhook secret, a private note. The apps keep their model keys and webhook secrets in it.

It is envelope encryption. A random data key encrypts the secrets, and the data key is wrapped under the admin password, and optionally under a platform secret.

After a restart it is locked, and it says so, until someone unlocks it. Without it you would build key wrapping, unlock and rotation yourself, or leave secrets in files and environment variables.

## 6 af_heart
Database access looks small, and solves a real problem. With a scaled-to-zero database, the first connection can arrive before the database is awake.

Here the database is down when the script starts. The kit retries with backoff, says what is happening, and connects as soon as it is up.

Next to it: a plain-SQL migration runner, with a migration table per app, a settings table, and the pgvector adapter. The nearest item by cosine distance comes back from an ordinary query.

The apps use it for their connections. Otherwise you would write retry logic, a migration tool and a settings table, again, for each app.

## 7 am_eric
Language models need two blocks. The first is a client in the kit that speaks the OpenAI-compatible API, with a guard for the address it calls.

Pointed at a local address, the guard refuses by default. One variable allows it, and the answer comes back from the real gateway running here. Cloud metadata addresses are always refused.

The second block is the gateway: a standalone, OpenAI-compatible service. Each app is a client, with its own revocable keys, its own models, a requests-per-minute limit, and a monthly token budget.

Models sit behind aliases, so repointing one alias moves every app to a new model. Without it, every app holds provider keys and limits of its own.

## 8 af_heart
The security middleware is one line on a FastAPI app. Every response gets the safe headers and a strict content security policy.

A browser write without the custom header is refused: that is the cross-site request forgery check. A body over the limit is refused too.

Every request is counted, under the metric names all the apps share. And the failed-login limiter lives in the authenticator: after ten bad tokens in a minute, the answer is four twenty-nine.

Otherwise you would write this once per app, and the copies would drift apart.

## 9 am_liam
Masking keeps personal data away from read-only database users, inside the database itself. The kit takes the base table away from the read-only role and grants a masked view instead.

The role gets permission denied on the table, and masked values through the view. The kit can re-apply the policy on a timer, because new grants reopen tables. This is the same policy, captured on the live fleet.

A second block lives in PayBroker: a hash-chained audit ledger, one SQL file, core Postgres only. Updates are refused. Even if an owner switches the triggers off, the verify function names the first broken entry.

This one is a pattern to copy: the file lifts out as is.

## 10 af_heart
Insights is a database page that the apps get from the kit: top queries from the monitor extension, tuner settings, and index suggestions from the query advisor. These are captured from the live fleet, because they need the EDB extensions.

Each source degrades politely. If an extension is missing, the page says it is unavailable, and why.

The metric names are the same in every app, so one dashboard fits all. Otherwise you would build a query page and a metrics convention for each app.

## 11 am_eric
The shared user interface is five small files, served from a path called kit. A light and dark theme, tables, badges, loading and error states, and accessible dialogs that replace the browser's native ones.

Contrast and accessibility are tested, and a test fails if shared code calls a native dialog. Without it, every app grows its own look, and its own bugs.

## 12 af_heart
Every app and both services ship the same operational surface: a Docker file, a health endpoint, a readiness endpoint, numbered migrations, and a metrics endpoint. So a component, or an app, deploys on AgentPG the same way.

For fleets there is the ecoctl tool: one manifest, and a dry run first. And an Ansible recipe with three small modules, for instances, sandboxes and extensions, which can be checked before they run. These are patterns to adapt, not packages.

## 13 am_liam
Inside the apps there is more worth taking. We label it honestly: patterns to copy.

Search: reciprocal rank fusion of vectors, full text and trigrams, in one SQL statement. ShopFront adds a typo-tolerant did-you-mean. The fusion is written three times, so a kit module is the obvious next step.

Maps: CityPulse has PostGIS areas and a nearby query. Its Brussels map data comes from OpenStreetMap, and needs attribution.

Live updates use the Postgres tcn extension, with no message broker.

And two small files lift out as is. ShopFront's webhook verification, standard library only. And real-city placement from the simulator: the same sensor, the same place.

## 14 af_heart
Put the blocks together, and a new app is small. The notes example is about two hundred lines of app, forty of wiring, eight of SQL, and sixty-nine of JavaScript.

It has first-run setup, login, API tokens, encrypted private notes, health and metrics. Everything else is the kit. And here it is, running.
